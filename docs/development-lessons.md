# 开发方法论与经验教训

> 从实际开发中提炼的原则，避免重复犯错。

---

## 一、实现功能前：先设计再动手

### 1. 画出完整数据流
在写任何代码之前，先明确数据从 A 到 B 到 C 的完整路径。

```
数据源头 → 中间处理 → 最终消费
```

每个箭头都是一个需要验证的接口。漏掉任何一个环节，功能就会断。

### 2. 查 API 再写代码
不要凭假设写代码。用到任何第三方库、系统 API、框架功能时，先查它的完整能力：
- 支持哪些参数？
- 有哪些回调？
- 返回什么类型？

**反模式：** "我觉得它应该不支持这个" → 直接写 → 后来发现它支持
**正模式：** 先查文档 → 发现它支持 → 直接用

### 3. 数据模型要覆盖所有关联场景
设计数据结构时，问自己：
- 谁会查找这条记录？
- 用什么字段匹配？
- 上下游都需要哪些字段？

宁可多一个字段，不要少一个字段。事后加字段的成本远高于一开始就设计好。

---

## 二、调试策略：逐环节验证

### 1. 复杂链路不要跳着写
如果功能涉及 5 个环节，不要写完第 1 和第 5 就期望它能工作。按顺序：
- 写完第 1 环节 → 验证
- 写完第 2 环节 → 验证
- ...以此类推

### 2. 用日志验证假设
不要假设"应该能工作"，要验证"确实能工作"。在关键节点加日志：
- 回调是否被调用？
- 数据是否正确传递？
- 状态是否正确更新？

验证通过后再删除日志。

### 3. 问题定位后才修改
不要盲目尝试修改。先定位根因：
- 是数据没产生？
- 是数据没传递？
- 是数据没消费？
- 是数据格式不对？

找到具体原因后再修改，否则改了也是碰运气。

## 三、架构原则

### 1. 关注点分离
- 数据层（Store）只管状态
- 业务层（Service）只管逻辑
- 展示层（Component）只管 UI
- 不要在一个地方混合多种职责

### 2. 避免隐式依赖
组件之间的依赖关系要显式声明（通过 props、events、store），不要依赖全局状态或副作用。

### 3. 错误处理要完整
每个异步操作都要考虑：
- 成功时做什么？
- 失败时做什么？
- 取消时做什么？
- 超时时做什么？

---

## 四、代码质量检查清单

实现功能后，自查：
- [ ] 数据流是否完整？每个环节是否验证过？
- [ ] 错误处理是否覆盖所有路径？
- [ ] 是否有未使用的代码（死代码）？
- [ ] 是否有硬编码的值应该提取为配置？
- [ ] 是否有安全隐患（注入、明文存储等）？
